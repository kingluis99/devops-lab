Before you begin

You already know Java, Spring Boot and Docker's basics — so the application layer is deliberately boring. Everything you build from Monday onwards is infrastructure, and every problem you hit will be an infrastructure problem. That is the whole design.

The one rule

Every change reaches every environment through a pipeline. Not scp. Not "just this once". The moment you hand-copy a jar onto the Pi, you have stopped learning DevOps and gone back to being a sysadmin.

Do this first

Keep a LEARNINGS.md in the repo from day one. Every time something breaks and you fix it, write three lines: symptom, cause, fix. In four weeks that file becomes your interview prep — and specific war stories beat "I have experience with Kubernetes" every single time.

Day 0 setup checklist

  • WSL2 + Ubuntu 24.04 installed; wsl -l -v shows VERSION 2
  • Docker Desktop installed with WSL integration enabled for Ubuntu
  • JDK 21 + Maven inside WSL; mvn -version works
  • VS Code with the WSL extension; repo lives in ~/projects, not /mnt/c
  • GitHub account with an SSH key added; ssh -T git@github.com authenticates
  • Pi reachable over SSH; docker ps -a snapshot saved before you touch anything
  • mvn clean verify passes on the starter project — 4 green tests
01

Linux & Git

The two things everything else stands on

By FridayYou are comfortable on a bare Linux shell, your project is on GitHub with branch protection, and a GitHub Actions pipeline runs your tests on every push.
Day 1

Filesystem, permissions, text

6–7 hrs
  • Navigate and inspect: pwd cd ls -la find grep -r less tail -f tree
  • Permissions until 755 vs 644 needs no thought: chmod chown, and what the three triads mean
  • Pipes and filters: | > >> grep awk sed sort uniq -c wc -l cut xargs
  • Learn enough vim to escape it: i, Esc, :wq, /search, dd

Drill: take any log file and answer, in one pipeline each — how many ERROR lines? which 5 IP addresses appear most? what were the last 20 lines before the first exception?

Done whenYou can answer those three questions without opening a browser.
Day 2

Processes, services, networking

6–7 hrs
  • Processes: ps aux, htop, kill vs kill -9, &, jobs, nohup
  • systemctl status/start/stop/enable and journalctl -u <svc> -f — the two commands you will use most on any real server
  • Networking: ss -tulpn, curl -v, dig, ping. Understand ports, and 127.0.0.1 vs 0.0.0.0
  • Write a systemd unit that runs the task-api jar, enable it, reboot, confirm it came back up
The one that catches everyone

A service bound to 127.0.0.1 is unreachable from outside its own machine — or, later, from outside its own container. Half of all "but it works locally" bugs are this. Learn to spot it in ss -tulpn output now.

Done whenThe jar restarts automatically after sudo reboot, and you can read its logs with journalctl.
Day 3

SSH, the Pi, and shell scripting

6–7 hrs
  • Key-based SSH to the Pi: ssh-keygen -t ed25519, ssh-copy-id, then a ~/.ssh/config entry so ssh pi just works
  • Harden the Pi: disable password auth and root login. Keep your current session open while you test the change.
  • Shell scripting: shebang, set -euo pipefail, $1, if/for, exit codes, trap
  • Write healthcheck.sh: curl /actuator/health, parse with jq, exit 0 if UP, log with a timestamp, schedule with cron
Done whenssh pi logs in without a password, password auth is off, and cron is appending health lines every 5 minutes.
Day 4

Git properly

6–7 hrs
  • Init the repo, .gitignore before the first commit, push to GitHub
  • The daily loop, ten times over: branch → edit → git add -p → commit → push → PR → squash merge → delete branch
  • Recovery commands: restore, reset --soft, commit --amend, stash, revert, reflog
  • Cause a merge conflict deliberately and resolve it. Then do it again.
  • Read history like an investigator: log --oneline --graph, blame, show <sha>, bisect
Know the difference

revert creates a new commit that undoes an old one — safe on shared branches. reset --hard rewrites history — safe only on a branch nobody else has. Getting this wrong on main is how people ruin a Friday afternoon for the whole team.

Done whenYou've resolved a conflict without googling, and recovered a "lost" commit with reflog.
Day 5

First pipeline: GitHub Actions

6–7 hrs
  • Read .github/workflows/ci.yml line by line. Know what on, jobs, steps, uses and run each do
  • Push and watch it run. Break a test on purpose; watch it go red; read the failure in the Actions log
  • Turn on branch protection for main: require the CI check, require a PR. Then try pushing straight to main and get rejected
  • Add a status badge to the README
  • Add a second job that only runs on main, and prove it skips on feature branches
Done whenA red pipeline physically prevents you from merging your own PR. That constraint is continuous integration.

Be able to explain

  • What a file's permission bits actually mean, and why chmod 777 is a smell.
  • The difference between a merge and a rebase, and when each is appropriate.
  • Why CI exists — what problem it solved that manual testing did not.
02

Docker

From "it works on my machine" to an image you can hand to anyone

By FridayA multi-stage, non-root, multi-architecture image of task-api is published to a registry by CI, and the same image runs on both your laptop and your Pi.
Day 6

Images, containers, layers

6–7 hrs
  • Core verbs: run, ps -a, logs, exec -it, stop, rm, images, rmi, inspect
  • Understand the image/container distinction properly — an image is a template, a container is a running instance with a writable layer on top
  • Run docker run -it ubuntu bash, install something, exit, run it again. Watch your change disappear. That is layer immutability
  • Write the simplest possible Dockerfile for task-api. Note the image size
Done whenYou can explain why a container that "does nothing" exits immediately.
Day 7

Dockerfile craft

6–7 hrs
  • Rewrite as a multi-stage build (JDK to build, JRE to run). Compare sizes — expect roughly 800MB down to 250MB
  • Order the layers for cache: COPY pom.xml and resolve dependencies before COPY src. Change one Java file and time the rebuild
  • Add a non-root user and a HEALTHCHECK. Understand why running as root inside a container matters
  • Write a .dockerignore. Check the build context size before and after
  • ARG vs ENV, CMD vs ENTRYPOINT — know which is overridable and when
Never bake in a secret

Anything you COPY or ENV into an image is visible to anyone who pulls it — docker history shows it even if a later layer deletes the file. Secrets come in at runtime, from the platform. This is a favourite interview question.

Done whenA one-line Java change rebuilds in seconds, not minutes, and docker history shows no JDK in the final image.
Day 8

Networks, volumes, and data that survives

6–7 hrs
  • Create a user-defined network. Run Postgres and task-api on it. Connect using the service name, not an IP
  • Named volumes vs bind mounts. Kill the Postgres container, recreate it, prove the data is still there
  • Port publishing: -p 8080:8080 — know which side is the host
  • Deliberately break it: point the app at localhost:5432 and understand exactly why it fails inside a container
Done whenYou can draw the two containers, the bridge network and the volume on paper, from memory.
Day 9

Compose, and the ARM64 lesson

6–7 hrs
  • Bring the whole stack up with docker compose up -d --build; read every line of the compose file
  • Add a healthcheck to the DB and depends_on: condition: service_healthy to the app. Understand why depends_on alone is not enough
  • Move the password out of the compose file into .env; confirm .env is gitignored
  • Copy the image to the Pi and run it. Watch it fail with exec format error
  • Fix it: docker buildx build --platform linux/amd64,linux/arm64 --push
This day is worth more than it looks

The AMD64-versus-ARM64 failure is the most instructive bug in the whole course. It forces you to understand that an image is not universal, that a registry stores a manifest list, and that "works on my machine" has a hardware dimension too. Write it up in LEARNINGS.md.

Done whenOne buildx command produces an image that runs unmodified on both machines.
Day 10

Registry, scanning, and CI that ships

6–7 hrs
  • Push to GitHub Container Registry from your laptop, then pull it on the Pi
  • Extend the Actions workflow to build and push on every merge to main, tagged with the commit SHA and latest
  • Add platforms: linux/amd64,linux/arm64 to the build step
  • Scan the image: docker scout cves or Trivy. Fix one real finding by moving to a newer base image
  • Deploy to the Pi with compose, pulling from the registry — no local build on the Pi
Done whenMerging a PR results, with no further action from you, in a new image on the registry that the Pi can pull.

Be able to explain

  • Why a container is not a VM, and what the kernel is doing (namespaces, cgroups).
  • Why tagging everything latest makes rollback impossible.
  • Where secrets should live, and why not in the image.
03

Pipelines

Jenkins — because the UK job market still runs on it

By FridayA Jenkins multibranch pipeline builds, tests, images, pushes and deploys task-api, gated by a quality check and a manual approval — and you can articulate how it differs from GitHub Actions.
Why Jenkins if Actions already works?

Because a large share of UK enterprise roles — banks, insurers, government, logistics — run Jenkins on-premise and will keep doing so for years. Actions teaches you CI/CD concepts faster; Jenkins is what the job advert asks for. You are learning both on purpose, and being able to compare them is itself an interview answer.

Day 11

Stand Jenkins up

6–7 hrs
  • Run jenkins/jenkins:lts-jdk21 in Docker with a persistent volume; unlock it and install the suggested plugins
  • Add the Docker Pipeline plugin; install the Docker CLI and kubectl inside the Jenkins container
  • Configure Tools: JDK named jdk21, Maven named maven3 — names must match the Jenkinsfile
  • Understand the controller/agent model, and why builds should not run on the controller in production
Done whendocker version and kubectl version --client both work from a Jenkins freestyle shell step.
Day 12

Your first Jenkinsfile

6–7 hrs
  • Create a Multibranch Pipeline job pointed at your GitHub repo
  • Declarative syntax: pipeline, agent, stages, steps, environment, options, post
  • Publish JUnit results and archive the jar; make a test fail and read the report Jenkins renders
  • when { branch 'main' } — prove a feature branch skips the deploy stages
Done whenJenkins discovers a new feature branch on its own and builds it without you creating a job.
Day 13

Credentials, images, and triggers

6–7 hrs
  • Store a registry token as a Jenkins credential; use it via docker.withRegistry. No secret in the repo, ever
  • Build and push the image from the pipeline, tagged with ${BUILD_NUMBER}
  • Trigger builds on push — poll SCM, or expose Jenkins through ngrok and set a real GitHub webhook
  • Grep the console output for your token and confirm Jenkins masked it
Done whenA git push starts a Jenkins build within a minute, with no secrets visible in the log.
Day 14

Quality gates and approvals

6–7 hrs
  • Add a JaCoCo coverage gate that fails the build below a threshold you set
  • Optional but worth it: run SonarQube in Docker and add a static-analysis stage
  • Add an input step before deploy — a human approval gate — with a timeout so it cannot hang forever
  • Add post { failure { ... } } notification to email or a Slack webhook
  • Deploy to the Pi over SSH from the pipeline: pull the new image, compose up -d
Done whenMerging to main gets you a Slack/email ping, an approval prompt, and then a running new version on the Pi.
Day 15

Consolidate and compare

5–6 hrs
  • Write a one-page comparison: Jenkins vs GitHub Actions — hosting, cost, plugins, secrets, agents, maintenance burden
  • Draw your full pipeline as a diagram: commit → CI → registry → deploy → health check. Put it in the README
  • Break the pipeline in three different places on purpose and fix each. Log all three in LEARNINGS.md
  • Catch up on anything that slipped — do not carry debt into week 4
Done whenYou can whiteboard the whole pipeline in under three minutes.

Be able to explain

  • Continuous integration vs continuous delivery vs continuous deployment — the differences are real and interviewers probe them.
  • Why the pipeline definition lives in the repo (pipeline-as-code) rather than in the Jenkins UI.
  • What mounting the Docker socket into Jenkins costs you in security, and what you would do instead in production.
04

Kubernetes & cloud

Scheduling, self-healing, and the vocabulary of the job market

By Fridaytask-api runs on Kubernetes on both k3d and the Pi's k3s, your pipeline deploys to it, you can perform a rolling update and roll it back, and you have stood up one cloud VM by hand.
Day 16

Cluster, pods, deployments, services

7–8 hrs
  • k3d cluster create devops-lab --agents 2; kubectl get nodes
  • Understand the object hierarchy: Pod ← ReplicaSet ← Deployment, and why you almost never create a Pod directly
  • Apply the Deployment and Service. Delete a pod by hand and watch a replacement appear — that is the control loop, and it is the whole idea
  • port-forward to reach the Service; curl /api/info in a loop and watch the hostname alternate between pods
  • Learn the diagnostic order by heart: get pods → describe pod (read the Events) → logs → logs --previous
Done whenTwo replicas are Ready and you have seen the load balancing with your own eyes.
Day 17

Config, secrets, storage, probes

7–8 hrs
  • ConfigMap for the DB URL; Secret for the password, created from the CLI rather than committed
  • Deploy Postgres as a StatefulSet with a PersistentVolumeClaim. Delete the pod; prove the data survived
  • Configure all three probes. Set the liveness probe too aggressively on purpose and watch Kubernetes kill your healthy app in a loop
  • Set resource requests and limits. Set the memory limit too low and meet OOMKilled
Base64 is not encryption

A Kubernetes Secret is base64-encoded, not encrypted, and anyone with read access to the namespace can decode it. Knowing that — and naming Sealed Secrets or an external vault as the real answer — is what separates a considered answer from a memorised one.

Done whenYou have deliberately caused CrashLoopBackOff and OOMKilled, and diagnosed each from describe alone.
Day 18

Rollouts, scaling, ingress

7–8 hrs
  • Rolling update: kubectl set image, then rollout status. Curl the app throughout and confirm zero dropped requests
  • Deploy a deliberately broken image, watch it fail, then kubectl rollout undo. Time yourself
  • Scale manually with kubectl scale, then add a HorizontalPodAutoscaler and generate load to trigger it
  • Expose through an Ingress; understand how it differs from a Service of type LoadBalancer
  • Wire the deploy into your pipeline: kubectl set image + rollout status, using the kubeconfig credential
Done whenA merge to main deploys to Kubernetes with no downtime, and you can roll back in under 30 seconds.
Day 19

The Pi cluster, and the cloud

7–8 hrs
  • Install k3s on the Pi; copy the kubeconfig to your laptop and drive the cluster remotely
  • Deploy the same manifests there. Tune replicas and memory requests to what a Pi can actually give you alongside Nextcloud
  • Set a billing alert, then create one cloud VM. Harden it exactly as you hardened the Pi
  • Run your image on it. Work out for yourself why port 8080 is unreachable and port 80 is — security groups
  • Write TEARDOWN.md, then follow it and delete everything
Cost discipline is a professional skill

Idle load balancers, unattached elastic IPs, NAT gateways and managed control planes are what turn a £0 experiment into a £60 surprise. Set the budget alert before you create anything, and tear down at the end of every session. Interviewers notice when a candidate mentions cost unprompted.

Done whenThe same image is running on three different machines, and the cloud one is deleted.
Day 20

Observability, and telling the story

6–7 hrs
  • Deploy Prometheus and Grafana into the cluster; scrape /actuator/prometheus
  • Build one dashboard that answers three questions: is it up, how fast is it, how much memory is it using
  • Set one alert rule and trigger it deliberately
  • Rewrite the README as a portfolio piece: architecture diagram, the pipeline, screenshots, and what you would do differently
  • Turn LEARNINGS.md into five STAR-format interview stories
Done whenYou could hand a stranger the repo URL and they would understand the whole system in five minutes.

Questions this project answers

Rehearse these out loud, using your own repo as the example

Walk me through your CI/CD pipeline.

Trace an actual commit: feature branch, PR, tests on GitHub Actions, branch protection blocking the merge until green, merge to main, multi-arch image built and tagged with the commit SHA, pushed to the registry, Jenkins deploying it to Kubernetes with a rolling update and a rollout status check. Naming the SHA tag and the rollback path is what makes this sound like experience rather than a tutorial.

How do you handle secrets?

Never in the image, never in the repo. Jenkins credentials or GitHub Actions secrets at build time; Kubernetes Secrets mounted as environment variables at runtime. Then volunteer the limitation — Kubernetes Secrets are base64, not encrypted — and name Sealed Secrets, External Secrets Operator or Vault as what you would reach for with real data.

A pod is in CrashLoopBackOff. What do you do?

kubectl describe pod and read the Events at the bottom first, then kubectl logs --previous to see the output of the instance that died. Most often it is configuration — a wrong datasource URL, a missing environment variable — or a liveness probe firing before a JVM has finished starting, which is exactly what a startupProbe exists to prevent.

Why multi-stage Docker builds?

Size and attack surface. The build stage needs a full JDK and a Maven cache; the runtime needs a JRE and a jar. Multi-stage takes the image from roughly 800MB to 250MB, keeps build tooling and source out of production, and shrinks what a scanner can find. Mention that you also run as a non-root user.

Container versus virtual machine?

A VM virtualises hardware and runs its own kernel; a container is an isolated process on the host kernel, fenced off with namespaces and cgroups. That is why containers start in milliseconds and VMs in tens of seconds — and why a container image is tied to a kernel architecture, which is the ARM64-versus-AMD64 problem you hit on your Pi.

What does Kubernetes actually give you over Docker Compose?

Reconciliation. Compose starts containers; Kubernetes continuously drives actual state toward declared state — rescheduling failed pods, replacing unhealthy ones, rolling updates out gradually and stopping if they fail. Add scaling, service discovery and declarative config, and say plainly that for a single-host side project Compose is often the right answer — knowing when *not* to use Kubernetes reads as judgement.

Tell me about something that broke and what you did.

This is where LEARNINGS.md pays for itself. The multi-arch failure is a strong story: symptom (exec format error on the Pi), diagnosis (docker inspect showing AMD64), fix (buildx multi-platform build), and the lasting change (platform matrix added to CI so it cannot recur). Symptom → diagnosis → fix → prevention is the shape every good answer takes.

Where to go next

In roughly the order the job market values them

Terraform

Infrastructure as code is the single most requested skill after Kubernetes. Recreate your cloud VM, network and firewall rules in HCL, then destroy and apply them back. Two days gets you an honest CV line.

Helm

Your k8s/ folder is four raw YAML files. Turn them into a chart with values for image tag, replicas and environment — this is how real teams ship the same app to dev, staging and prod.

GitOps — Argo CD

Instead of the pipeline pushing to the cluster, the cluster pulls from Git. Increasingly the default in Kubernetes shops, and a natural evolution of what you already built.

Ansible

Configuration management for the machines that are not containers. Codify the Pi hardening you did by hand in week 1 and you have a real playbook, not a toy one.

Observability, properly

Structured JSON logging, Loki for aggregation, distributed tracing with OpenTelemetry. Then define an SLO for task-api and mean it.

Certification, if you want the badge

The CKA is hands-on and genuinely respected. Everything in week 4 is on the syllabus. AWS Solutions Architect Associate is the broader alternative if you lean cloud.

A word on pace

Four weeks at this intensity is demanding, and the days where nothing works are the days you learn most — that is not a setback, it is the curriculum. If a week slips, cut scope inside the week rather than dropping a week; each one depends on the one before it. And if only three weeks are available, drop the cloud day and the observability day, not Docker or Kubernetes.
